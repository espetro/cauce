# oxe v3: Rust core, modular metasearch with a hybrid cache

**Status:** proposal, awaiting owner approval. Nothing in this document is implemented.
**Supersedes:** `2026-09-17-v0.5.0-archive-rebuild.md` (v2) as the authoritative plan once approved.
**Keeps:** `legacy` branch as v1 (PyPI 0.4.0). Proposes archiving the current `main` as `v2`.

## 1. Why a third attempt

Two attempts (v1 `legacy`, v2 `main`) produced code that passes its own gates and does not
work end to end. Measured on 2026-09-21 against the real stack (details in the session
findings, summarised here so this plan does not depend on chat history):

| Failure | Root cause | Class |
|---|---|---|
| First search intermittently 502s, AI tool calls fail, page 2 always 502 | Only engine is `ddgs` `duckduckgo`; from this machine it fails 4/5 queries and cannot page. `google` and `mojeek` also 0/3. `bing` 3/3, `yahoo` 3/3, `brave` 2/3 (fastest). | upstream choice, no fallback |
| Continuous scroll spins forever | Sentinel ref never attached; button dispatches state but fetch lives in the observer | wiring |
| History and dashboard permanently empty | `SearchService` never writes `search_log`; nothing writes `clicks`; no click endpoint | wiring |
| Settings dialog blank in dev | Vite proxy lacks `/settings`; load failure swallowed | wiring |
| MCP and Exa adapter unreachable | Modules complete and tested, never mounted in `create_app()` | wiring |
| "cached" badge, no TTL/age anywhere | `/search` exposes no cache metadata; badge is a hardcoded button | missing contract |
| AI "streaming" is one delta after 12s; ungrounded answers cached | Blocking provider call; cache gate is model self-confidence, not sources | design |

The verification stack never touched any of these: e2e ran on `wikipedia-opensearch` and
`force=` fixtures (6 pass, 14 skipped), the UI loop's hard gates measure console errors and
axe, unit tests swap the service for fakes. Modules were verified in isolation; the arrows
between them were never a test subject.

Conclusion carried into v3: **the golden path against a real provider and a deterministic
provider is the first artifact, not the last**, and every mounted surface is asserted by a
test that reads the live router table.

## 2. Goals and non-goals

Goals (from the owner, 2026-09-21):

1. Metasearch tool shared by humans (web UI) and agents (HTTP API, MCP) with a TTL cache, so
   a human's lookup is instantly reusable by an agent and vice versa.
2. A modular, better-architected alternative to SearXNG: tail-tolerant scheduling instead of
   wait-for-slowest, engine health and circuit breakers, pluggable engines that contributors
   can fix without recompiling.
3. Core + API/MCP + web UI usable early, with 2 real providers we heavily use (Bing, Brave HTML)
   plus 1 deterministic provider (`replay`) immune to rate limits so agents iterate fast.
4. Runs locally as an OS service under SearXNG's baseline (target: < 80 MB RSS idle, single
   static binary), and is architected so an enterprise deployment is a config change (store
   backend, egress, auth), not a rewrite.
5. Observability that answers "is this result grounded, when was it fetched, what is its TTL,
   which engines contributed, which cache tier served it".

Non-goals for v3.0:

- A general web crawler or independent index.
- Public multi-tenant instance hardening (anti-bot on our own front door, per-user quotas).
- Feature parity with SearXNG's 70+ engines. We ship 2 native + a bridge and a contract others
  can fill.
- Semantic (vector) cache in the first release. It is a feature-flagged tier with a defined
  seam; it lands after the lexical tiers are proven.

Dependency direction is one way: `oxe-server` -> `oxe-engines`, `oxe-store-sqlite` -> `oxe-core`.
`oxe-core` depends on no I/O crate other than `tokio` and `reqwest` behind the `HttpClient`
trait. This is what makes the enterprise swap a config change.

### 4.2 Core contracts (exact shapes, so wave 0 does not guess)

```rust
// oxe-core
pub struct SearchRequest { q: String, page: u8, lang: Option<String>, time_range: Option<TimeRange>,
                           safesearch: SafeSearch, engines: Option<Vec<EngineId>>, client: ClientKind }
pub struct SearchResult  { url: Url, title: String, snippet: String, engine: EngineId,
                           published: Option<DateTime>, score: f32 }
pub struct SearchMeta    { source: Source /* Cache{tier,age_s,ttl_s} | Network */, engines_used: Vec<EngineReport>,
                           deadline_hit: bool, elapsed_ms: u32, request_id: Uuid }
pub struct SearchResponse{ query: String, results: Vec<SearchResult>, meta: SearchMeta }

#[async_trait] pub trait Engine: Send + Sync {
    fn id(&self) -> EngineId;  fn tier(&self) -> Tier;  fn page_size(&self) -> u8;
    async fn search(&self, req: &SearchRequest, budget: Duration) -> Result<Vec<SearchResult>, EngineError>;
}
pub enum EngineError { RateLimited, Blocked /* captcha */, Timeout, Parse(String), Transport(String), NoResults }

#[async_trait] pub trait Store: Send + Sync {
    async fn get_exact(&self, key: &CacheKey) -> Result<Option<CachedSearch>>;
    async fn get_lexical(&self, q: &str, limit: u8) -> Result<Vec<CachedSearch>>;   // FTS5 over query + titles
    async fn put(&self, key: &CacheKey, resp: &SearchResponse, ttl: Duration) -> Result<()>;
    async fn evict_expired(&self) -> Result<u64>;
    async fn log_search(&self, row: SearchLogRow) -> Result<()>;
    async fn record_click(&self, row: ClickRow) -> Result<()>;
    async fn health(&self) -> Result<Vec<EngineHealthRow>>;  async fn put_health(&self, ..) -> Result<()>;
    // stats/history/cache-admin read methods, see DATA section
}
```

`CacheKey` = sha256 over (normalised `q`, page, lang, time_range, safesearch). Engine
selection is deliberately not in the key: a hit is a hit regardless of which engines produced
it (the v2 property). `meta.engines_used` tells the consumer where it came from.

### 4.3 Engine runtimes

**Declarative (YAML)** covers Bing, Brave, Wikipedia. Schema (v1):

```yaml
id: brave
tier: 1                       # 1 fast/reliable, 2 hedge, 3 specialised
page_size: 10
request:
  url: "https://search.brave.com/search?q={q}&offset={page0}"
  headers: { Accept-Language: "{lang}" }
  timeout_ms: 2500
parse:
  kind: html                  # html | json
  results: "div.snippet[data-type=web]"
  fields:
    title:   { css: ".title", text: true }
    url:     { css: "a", attr: href }
    snippet: { css: ".snippet-description", text: true }
detect:
  blocked:  [ "captcha", "unusual traffic" ]   # body substrings -> EngineError::Blocked
  rate_limited_status: [429, 403]
```

The runtime compiles selectors once, fetches with the shared `HttpClient` (rustls, UA
rotation, per-engine concurrency cap), parses with `scraper`, and maps to `SearchResult`.
Every spec ships with a `fixtures/<id>/<query>.html` and an expected JSON; `oxe engine test
engines/brave.yaml` runs the fixtures offline and `--live` runs a canary query.

**Exec (JSON over stdio)** is the language-agnostic contract, identical in spirit to LSP/MCP:

```json
→ {"v":1,"query":"tail tolerance rust","page":1,"lang":"en","timeout_ms":1500}
← {"v":1,"results":[{"title":"...","url":"...","snippet":"..."}],"error":null}
```

One process per engine, kept warm, restarted on crash, killed at deadline. `sdk/python`
provides `oxe_engine_sdk.run(fn)`, and `engines/ddgs_auto.py` (30 lines) is the reference
engine and the day-1 bridge.

**Replay** loads cassettes recorded by `oxe record --engine bing --query ...` (raw response +
parsed results) and serves them deterministically, keyed by normalised query. Synthetic mode
generates N plausible results from a seed and honours `OXE_REPLAY_LATENCY_MS`,
`OXE_REPLAY_FAIL_EVERY`, `OXE_REPLAY_BLOCKED` so scheduler behaviour (hedge, breaker, deadline)
is testable without the network. This is the engine the golden path and the UI iterate on.

### 4.4 Scheduler (the SearXNG difference)

1. `t=0` cache lookup, tiers in order; a fresh tier-1 hit returns immediately; a stale hit is
   returned with `meta.source=Cache{stale:true}` and triggers a background refresh.
2. `t=0` fan out to all **healthy tier-1** engines (Bing, Brave) with the request budget.
3. `t=P90(tier1)` (EWMA-derived, floor 300 ms): if fewer than `min_results` (default 5) have
   arrived, hedge to healthy tier-2 engines (`ddgs` bridge, later Yahoo/Startpage).
4. Hard deadline (default 2500 ms live, configurable): cancel in-flight futures, merge what
   arrived, set `meta.deadline_hit`.
5. Merge: dedupe by normalised URL (scheme, host lowercase, strip tracking params, trailing
   slash), score by RRF across engines, stable order.
6. Health: per-engine EWMA latency (`alpha=0.3`), failure counter, breaker states
   Closed/Open/HalfOpen. `RateLimited`/`Blocked` open the breaker for 15 min, `Timeout` x3 in
   a row for 5 min. Persisted in `engine_health` so a restart does not hammer a blocked engine.
7. Streaming variant (`/api/search/stream`, and the HTMX page): emit `results` SSE events as
   each engine returns; the client appends below the fold, never reorders visible items;
   a final `meta` event closes the stream.

### 4.5 AI mode (wave 4, deliberately late)

Provider call is streamed (SSE from OpenAI-compatible endpoint), tool loop over
`search_web`/`search_archive`, answer cached only when `sources.len() >= 1` and confidence
above threshold, `answer` responses carry `meta` like searches. Not in the golden path for
v3.0 because it depends on a paid provider and was the least broken part of v2.

## 5. Data model (the DATA.md that was missing)

SQLite, WAL mode, one file. Every table has exactly one writer path; that is asserted by a
test that greps `Store` impl call sites (see section 7).

| Table | Purpose | Written by | Read by |
|---|---|---|---|
| `cache_entries(key PK, query, params_json, payload_json, created_at, expires_at, hits, engines_json)` | tier-1 exact cache | `Pipeline::persist` | tier-1 lookup, cache admin UI/API, stats `cache` panel |
| `cache_fts` (FTS5, external content on `cache_entries`: query, titles, snippets) | tier-2 lexical cache + `search_archive` | trigger on `cache_entries` | tier-2 lookup, MCP `search_archive` |
| `cache_vec(key, embedding BLOB)` (feature `semantic`) | tier-3 semantic | `Pipeline::persist` when enabled | tier-3 lookup |
| `search_log(id, ts, query_hash, query, client, source, tier, latency_ms, result_count, engines_json, deadline_hit)` | every search request, cache or network | `Pipeline::respond` (unconditional) | history page, dashboard (per day, hit rate, latency percentiles, client split, zero-result queries) |
| `clicks(id, ts, query_hash, url, title, position, client)` | result click-through | `POST /api/click` (UI beacon) and MCP `record_visit` | history page, `user_history` MCP tool, AI `search_archive` boost |
| `engine_health(engine_id PK, ewma_ms, failures, breaker_state, breaker_until, last_ok_at, last_error)` | scheduler state across restarts | `Scheduler` | scheduler, `/api/engines`, engines page |
| `answers(key PK, query, model, payload_json, sources_json, created_at, expires_at)` | AI answer cache (wave 4) | `answer` route | `answer` route, dashboard |
| `pages(url PK, fetched_at, title, markdown, ...)` + `pages_fts` | archived reader pages (wave 5) | `fetch_and_index` | `search_archive` |

Rules:

- `search_log` is written for **every** request including cache hits, so "hit rate" is
  `count(source=cache)/count(*)`, not `unexpired/rows` (the v2 dashboard's mistake).
- History and dashboard read the same plane (`search_log` joined to `clicks`), fixing the
  "two unsynced data planes" retro item.
- TTL: default 1 h, per-request override capped at 24 h, `evict_expired` every 5 min on a
  tokio interval; `DELETE ... WHERE expires_at < now` on the B-tree index.
- Postgres impl mirrors this schema with `tsvector` replacing FTS5 and `pgvector` for tier 3.

That is the mechanical fix for "written but never mounted".

## 7. Verification policy (the part v1 and v2 did not have)

1. **Golden path, wave 0, always green.** An integration test builds the binary, starts it
   with `OXE_ENGINES=replay` and a temp DB, then in one flow: `GET /api/search` (network) ->
   same query again (`meta.source=Cache`, `age_s > 0`) -> `GET /api/history` has 2 rows ->
   `GET /api/stats` hit rate is 0.5 -> `POST /api/click` -> history shows the click -> MCP
   `search_web` via rmcp client returns the cached result with `meta` -> `POST /search` (Exa)
   returns the same URLs -> `DELETE /api/cache/{key}` -> search is network again. Plus the
   HTMX `/search?q=` page contains the result titles and the `cached` badge text with age.
2. **Replay first, live gated.** Everything in CI runs on `replay`. `OXE_LIVE=1 cargo test
   --test live` runs Bing + Brave canaries and records fixture drift; it runs nightly and on
   demand, never blocks merges.
3. **Engine fixtures.** Each YAML ships recorded HTML + expected JSON; `oxe engine test` runs
   them in CI. A selector change without a fixture update fails.
4. **Wiring matrix tests.** (a) routes table vs live router vs this document, (b) every `Store`
   write method has exactly one call site in the pipeline (grep-based test, like v2's
   `test_agents_rules.py`), (c) every `Engine` impl is constructible from config.
5. **Resource budget test.** Release binary starts, serves 100 replay searches, RSS stays
   under 80 MB and binary under 30 MB (measured, thresholds tunable in one file).
6. **No fixture-only screens.** A UI template may not ship a state the golden path or an
   engine fixture cannot reach. `force=` style fixtures are gone; the `replay` synthetic mode
   provides empty/error/slow states.
7. Gates: `cargo fmt --check`, `clippy -D warnings`, `cargo test` (incl. golden path), `cargo
   deny` (licenses: MPL-2.0 core must not pull GPL), `oxe engine test`, size/RSS budget. One
   `just validate` / `mise run validate`; CI runs it on every push; pre-push hook runs it.

## 8. Waves

Each wave ends with the golden path green and the binary replacing the previous one in
`~/.config/oxmgr/oxfile.toml` when it is at least as usable. No wave ships a surface the
golden path does not exercise.

**Wave 0: skeleton that searches (replay only).** Workspace, CI, `oxe-core` types and traits,
`oxe-store-sqlite` with `cache_entries`/`search_log`/`clicks`, `replay` engine, pipeline
without hedging (parallel + deadline), `GET /api/search`, `/api/history`, `/api/stats`,
`/api/click`, cache admin routes, HTMX search page with results + meta badge. Golden path test
passes. Exit: `oxe serve` + browser search on replay end to end.

**Wave 1: real results and agent surfaces.** Declarative engine runtime + `bing.yaml`,
`brave.yaml`, `wikipedia.yaml` with fixtures; `exec` runtime + Python SDK + `ddgs_auto.py`
bridge; breaker + EWMA persisted; Exa `POST /search`; MCP over streamable HTTP and stdio with
`search_web`, `cache_*`, `exa_search`. Exit: `~/SEARCH.md` wiring (Claude Code, Hermes) works
against v3 on port 4479 via oxmgr; live canary green for Bing and Brave.

**Wave 2: usable UI and observability.** SSE progressive results on the search page, history,
dashboard (from `search_log`), cache page (list, inspect payload, delete), engines page
(health, breaker reset), settings page, theme. Mobile layout. Exit: owner uses it daily for a
week; findings become wave-3 input.

**Wave 3: tail tolerance.** P90 hedge to tier 2, stale-while-revalidate, `min_results`, RRF
tuning, `oxe engine test --live` canary CLI, nightly live workflow, fixture drift report.

**Wave 4: AI mode.** Streamed provider calls, tool loop, grounded-only caching, answer page.

**Wave 5: archive.** `fetch_and_index` (readability -> markdown), `pages` + FTS, MCP
`search_archive`, optional `semantic` feature (fastembed INT8 + sqlite-vec or brute force).

**Later, not scheduled:** Postgres `Store`, QuickJS engine runtime, OTA engine registry, TS
SDK, `searxng-upstream` engine (use an existing SearXNG as a tier-2 source).
